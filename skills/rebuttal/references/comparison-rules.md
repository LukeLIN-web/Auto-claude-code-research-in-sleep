# Evidence and comparison rules

Read before writing any number or baseline comparison into a response file (Phase 4) and when running the Phase 5 comparison scan. These rules sit under "Never expose a weakness" and "What 'explicitly asked' covers" in `SKILL.md`.

- **Minimum sufficient evidence per concern.** Usually one numerical anchor: the metric that maps directly to *that reviewer's* specific ask. Cut metrics other reviewers care about — bloat dilutes the answer.
- **A measurable ask gets the measurement.** When the reviewer asks for latency, FLOPs, memory, a count or a breakdown, the reply carries that number. A derivation plus a camera-ready promise is what the AC records as unresolved (VQToken meta-review: "left … overhead issues unresolved"; [case-vqtoken-neurips2025.md](case-vqtoken-neurips2025.md)).
- **Choosing what to compare on** (user 2026-11-07: 「统一」「补」). Once the comparison is mandatory, the metric decides what the reply exposes:
  - *One metric for every baseline in a reply.* Pick it once per reply. The default is the paper's headline metric for that component. Use it for every baseline the reply compares against. Reporting metric M against baseline A, where we win, while dropping M against baseline B, where we lose, is metric shopping that a reader sees within the same reply. A baseline we beat on no shared metric gets only the structural or format argument (`structural_distinction`), with no number.
  - *Every win is written; the interval decides only how* (user 2026-11-07: 「如果我们赢了, 区间含 0 也可以写」). Before a favorable comparison enters a draft, compute a paired bootstrap 95% interval of the gap. Resample the unit the claim generalizes over: videos or items for per-item claims, prompts or tasks for benchmark-level claims. Record the interval in the issue card.
    - If the interval excludes 0, write the win with the interval, or call the gap significant.
    - If the interval includes 0 but the point estimate favors us, still write the win, as the two point estimates ("5.5% vs 6.8%"). Print no interval and no significance word, since either would expose that the gap is not established.
    - For metrics built from absolute values (|bias|, mean |error|), record the basic interval next to the percentile one, because resampling pushes them up when the true gap is small.
  - *A tie is not a win.* Do not state "on par with", "comparable to" or "no worse than" a baseline. A point estimate in our favor is written as the two numbers, not as a tie.
  - *Skip metrics that bring in a named winner.* If reporting metric M would call for listing a reviewer-named baseline that beats us on M, do not use M anywhere in that reply.
  - *No numbers a reader can line up against the paper to show the flagship losing.* Before-and-after gains of our own variants are fine. An absolute value that beats the flagship's number in a paper table is not, for example a variant's rank correlation above the flagship's. Report such variants only on metrics where the flagship is not beaten.
  - *State the format difference precisely.* Say what the baseline outputs (one holistic score, binary labels, fixed yes/no flags) against what ours outputs (graded per-criterion scores). Do not write that it "cannot" do something that one of its modes can do.
- **One measurement setup for every arm** (user 2026-11-10: 「重新测一测, 统一口径.」「用我们性能最好的方法」「统一.」). A time or memory comparison holds only when every arm runs the same way: same card, same media decoding and its parallelism, same batching, same caching, back to back. Before writing a cost number, list each arm's setup and check that they match. A gap that comes from the setup is not the method's: one draft's "about 8 s faster" came from our arm decoding media on 8 processes while the baselines decoded in one; with every arm on the same 8-process pool the gaps went both ways by a few seconds. When the setups differ, re-measure every arm on our best setup (here the 8-process decode pool); do not slow our arm down to match. Check that the change touched only how inputs are obtained (here pooled and one-process decoding gave byte-equal inputs), then rewrite every reply that carries the number.
- **Weak number → "the best of the rest is weaker still"** (user 2026-11-09, on a W2 reply: 「如果说不好, 就写 别人的最好的也不如我们好」). When a reviewer quotes a number of ours that cannot be defended as high in absolute terms (e.g. a split-half ρ of 0.38), do not argue that it is high. Put it next to the best that other methods reach on the same quantity: "the strongest existing evaluator reaches only Y". Conditions, all required:
  - *Same quantity.* Measure the others on our data with the identical protocol (same units, same aggregation, same resamples), e.g. judge-vs-one-human-half ρ against human half-vs-half ρ. Literature numbers on another benchmark or another unit (per-video vs per-model correlation) may be cited only as context, with their unit stated, never in the same column.
  - *Measured, and it holds.* Run it before writing it; the claim covers exactly the cells where our number is above the best other one. Cells where it is not are left out under "Never expose a weakness"; if the reviewer named that cell, mark `needs_user_input`.
  - *No named winner over our flagship.* If the comparison table would show a baseline beating our own method (not just our reference data) on that quantity, "Skip metrics that bring in a named winner" applies: compare only against what is not our method, or escalate.
- **Words agree with numbers.** Every evaluative word ("improves", "outperforms", "maintains") must be true of the numbers printed next to it. VQToken called 78.59 vs 81.40 "not only maintains but improves performance".
